# ORDERS SERVICE — AUDITORÍA Y MODELO DE DATOS PROPIO (PROMPT 3.0)

Informe de auditoría y propuesta de modelo de datos **independiente** para `orders-service`,
basado **únicamente en evidencia de código** (`V1__init.sql`, DTOs de persistencia,
adaptadores, casos de uso y modelos de dominio).

Fuente de verdad de contratos: `TEAM_INTERNAL_API_CONTRACTS.md`.

---

## 1. Estado actual de BD

orders-service se conecta a un único esquema Supabase compartido donde **todos** los
servicios coexisten. El DDL canónico es `juniors/.../orders-service/src/main/resources/db/migration/V1__init.sql`
(Flyway). Existen también seeds en `supabase_migration.sql`, `database.sql` (legacy MySQL)
y `.../migration_local/V1_1__seed_local_data.sql` (H2 local con todo el monolith).

Las relaciones entre tablas se expresan con FK a nivel de BD compartida. Tras la Etapa 2,
orders-service **solo debe acceder** a `orders`, `order_items` y `client`; el resto
(`products`, `restaurant`, `users`, `delivery`, `delivery_routes`) se resuelve por HTTP.

Estado de implementación actual:
- `SupabaseRestOrderRepositoryAdapter` persiste/lee `orders` y `order_items` (PostgREST al
  schema de Orders). Mapeo `mapToOrder` ya no realiza joins a tablas externas.
- `SupabaseRestClientAdapter` (portada PROMPT 2) accede a la tabla propia `client`.
- Los servicios externos se consumen vía adapters HTTP (Catalog C-1..C-3, Auth C-4,
  Delivery C-5..C-7), inyectados en los use cases / `OrderEnricher`.

| Tabla | Propietario propuesto | Uso (evidencia) |
|---|---|---|
| `orders` | **Orders** (propia) | `SupabaseRestOrderRepositoryAdapter`: save, findById, findAll(restaurantId), updateStatus, claimOrders, countActiveOrdersByDelivery, findByIdsForClaim, findByIds. Origen del id externo Long. |

| `products` | Catalog | Se consumía vía SQL directo → **reemplazado** por C-1 (HTTP). NO pertenece a Orders. |
| `restaurant` | Catalog | Se consumía vía SQL directo → **reemplazado** por C-2/C-3 (HTTP). NO pertenece a Orders. |
| `users` | Auth | Se consumía vía SQL directo → **reemplazado** por C-4 (HTTP). NO pertenece a Orders. |
| `delivery` | Delivery | Se consumía vía SQL directo → **reemplazado** por C-5 (HTTP). NO pertenece a Orders. |

## 3. Dependencias encontradas

| Dependencia | Tipo | Debe eliminarse |
|---|---|---|
| `orders.restaurant_id` → `restaurant.id` | FK SQL | Sí (reemplazada por C-2/C-3). Se conserva como columna referencia externa. |
| `orders.delivery_id` → `delivery.id` | FK SQL | Sí (reemplazada por C-5). Se conserva columna referencia externa. |
| `orders.client_id` → `client.id` | FK SQL | No — cliente es propio de Orders. |
| `order_items.product_id` → `products.id` | FK SQL | Sí (no hay join en Orders; precio se snapshottea). Se conserva referencia externa. |

| `delivery_routes.order_id` → `orders.id` | FK SQL | Sí — tabla trasladada a Delivery. No pertenece al schema de Orders. |

## 4. Modelo propuesto (BD independiente de Orders)

Tablas propias de Orders: **`orders`**, **`order_items`**, **`client`**.

Todas las referencias a otros servicios se guardan como **IDs externos (Long)** sin FK
(la integridad se valida por HTTP, no por el schema). El owner de la relación de
*`orders.client_id → client.id`* se mantiene como FK interna.

### `orders` (propuesta)
```sql
CREATE TABLE orders (
  id              BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  client_id       BIGINT NOT NULL,
  restaurant_id   BIGINT NOT NULL,                       -- ref externa a Catalog
  delivery_id     BIGINT,                                 -- ref externa a Delivery
  status          TEXT   NOT NULL DEFAULT 'Nuevo pedido',
  address         TEXT   NOT NULL,
  subtotal        NUMERIC(12,2) NOT NULL DEFAULT 0,
  delivery_fee    NUMERIC(12,2) NOT NULL DEFAULT 0,
  total           NUMERIC(12,2) NOT NULL DEFAULT 0,
  payment_method  TEXT   NOT NULL DEFAULT 'Efectivo',
  created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
  CONSTRAINT fk_orders_client FOREIGN KEY (client_id) REFERENCES client(id) ON DELETE RESTRICT
);
```

### `order_items` (propuesta)
```sql
CREATE TABLE order_items (
  id              BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  order_id        BIGINT NOT NULL,
  product_id      BIGINT NOT NULL,                      -- ref externa a Catalog
  quantity        INTEGER NOT NULL DEFAULT 1 CHECK (quantity > 0),
  unit_price      NUMERIC(12,2) NOT NULL,
  total           NUMERIC(12,2) NOT NULL,
  CONSTRAINT fk_order_items_order FOREIGN KEY (order_id) REFERENCES orders(id) ON DELETE CASCADE
);
-- (O) snapshot recomendado: product_name TEXT, product_description TEXT, product_image TEXT
```

### `client` (propuesta)
```sql
CREATE TABLE client (
  id            BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id       BIGINT NOT NULL UNIQUE,                  -- ref externa a Auth (C-4)
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  end_date      TIMESTAMPTZ
);
```

### Tabla excluida intencionalmente
- **`delivery_routes`**: pertenece a Delivery. No se crea en el schema de Orders.
  El campo `Order.route` quedará `null` en lecturas hasta que Delivery exponga un
  contrato de lectura (ver §5 / §12). El seed local `V1_1__seed_local_data.sql` dejará
  de insertar/crear `delivery_routes` (asunto de PROMPT 3-implementación).

## 6. Relaciones internas de la BD

```
orders 1 ────< order_items        (order_id → orders.id, ON DELETE CASCADE)
orders }───── client               (client_id → client.id, ON DELETE RESTRICT)

orders ─ restaurant_id ──> Catalog.restaurant.id    (NO FK local, ref externa Long)
orders ─ delivery_id    ──> Delivery.delivery.id     (NO FK local, ref externa Long)
order_items ─ product_id ──> Catalog.products.id      (NO FK local, ref externa Long)
client ─ user_id ──> Auth.users.id                    (NO FK local, ref externa Long; UNIQUE)
```

`delivery_routes` y `orders.delivery_id` referencian Delivery, pero **no** existe FK entre
ellos en el schema independente (no hay tabla local `delivery_routes`); `delivery_id` se
guarda como referencia externa.

## 8. Índices

Basados en queries reales del adaptador/repositorio:

| Tabla | Índice | Motivo (evidencia) |
|---|---|---|
| orders | PK (id) | `findById`, `updateStatus` filtran por `id` |
| orders | idx `client_id` | históricamente filtrado por cliente; se conserva |
| orders | idx `restaurant_id` | `findAll(restaurantId)` (ListOrdersUseCase) |
| orders | idx `delivery_id` | `countActiveOrdersByDelivery(deliveryId)` |
| orders | idx `(delivery_id, status)` | `countActiveOrdersByDelivery` filtra `delivery_id` + `status IN (En camino, Retirado)` |
| orders | idx `status` | consultas futuras de órdenes por estado |
| orders | idx `created_at` | listados ordenados por fecha |
| order_items | PK (id) + idx `order_id` | lectura de ítems por pedido (`findById`) |
| client | UNIQUE `user_id` | `findClientIdByUserId` asume un cliente por usuario |

> `idx_order_items_product` (sobre `product_id`) se propone **eliminar** en el schema de
> Orders: Orders no filtra `order_items` por `product_id`; esa query pertenece a Catalog.

## 9. Constraints

- PK: `orders(id)`, `order_items(id)`, `client(id)`.
- FK internas: `orders.client_id → client(id) ON DELETE RESTRICT`;
  `order_items.order_id → orders(id) ON DELETE CASCADE`.
- UNIQUE: `client.user_id` (one-client-per-user).
- CHECK: `order_items.quantity > 0`; `orders.subtotal/delivery_fee/total >= 0` (recomendado).
- DEFAULT: `status='Nuevo pedido'`, `subtotal/delivery_fee/total=0`, `payment_method='Efectivo'`,
  `created_at=now()`.
- FK a `restaurant`, `delivery`, `users`, `products`: **NO** existen (refs externas sin FK).

## 10. Migración de datos

- **Copiar directamente**: `orders`, `order_items`, `client` (filas y columnas actuales) —
  los IDs externos (`restaurant_id`, `delivery_id`, `product_id`, `user_id`) son Long y
  **se conservan tal cual** (referencian otros servicios; la integridad ya no se impone vía FK).
- **Transformación**: UUID↔Long no afecta la BD; se resuelve en el adapter (`IdConverter`).
- **No reconstruir**: `delivery_routes` no migra a Orders (pasó a Delivery).
- **Snapshot de producto**: los valores históricos de `product_name/description/image` no
  existen hoy en `order_items`; si se adoptan las columnas propuestas (§5), la migración
  deberá poblarlas retroactivamente vía Catalog C-1 (asunto de PROMPT 3-implementación).
- El seed local `V1_1__seed_local_data.sql` deberá dejar de crear/insertar `delivery_routes`
  y `users/restaurant/delivery/products` en el schema de Orders (asunto de PROMPT 3).

## 11. Archivos afectados posteriormente (PROMPT 3-implementación)

- `orders-service/.../resources/db/migration/V1__init.sql` → nuevo DDL Orders-only (3 tablas,
  sin FK externas).
- `orders-service/.../resources/db/migration_local/V1_1__seed_local_data.sql` → seed local

- `OrderRepositoryPort` / `SupabaseRestOrderRepositoryAdapter` → persistir/leer snapshot de

- `OrderEnricher` → enriquecer `OrderItem.productName/description/image` vía C-1 (ver §12).
- `.env` / profiles → apuntar orders-service a su propia BD (supabase.url dedicada).

## 12. Riesgos / dudas (bloqueos reales vs. decisiones)

1. **Snapshot de producto en `order_items` (bloqueo de información).** El modelo de dominio
   `OrderItem` lleva `productName/description/image` y la respuesta `OrderDetailResponse.ItemDto`
   los expone. Hoy `order_items` **no** los persiste y el adapter no los enriquece → en lectura
   quedan `null`.
   - Opción A (recomendada): enriquecer en `OrderEnricher` con `CatalogPort.findProductsByIds`
     (C-1, contrato existente) → lectura "live", sin cambio de schema.
   - Opción B: agregar columnas snapshot a `order_items` → lectura autocontenida, histórico fiel.
   - Decisión pendiente del equipo (no se inventa en este prompt).

2. **`DeliveryInfo` y `Order.route` (pendiente contractual).** No existe contrato en C-1..C-7
   para: obtener repartidor por `delivery_id` (C-5 es por `userId`) ni leer la `delivery_routes`
   de un pedido. Por tanto `order.deliveryInfo` y `order.route` quedan `null` en lectura.
   Documentado como pendiente; no se inventa endpoint.

3. **Propiedad de IDs**: `orders.restaurant_id`/`delivery_id`/`order_items.product_id`/
   `client.user_id` son Long externos. Se proponen como columnas sin FK. Si en el futuro
   Orders necesita validar pertenencia, hacerlo vía HTTP (no via FK entre BDs).

4. **Tipo de PK propio**: se recomienda mantener `bigint` (Long) para `orders/id`,
   `order_items/id`, `client/id`, coherente con la contract C-8 (respuesta Long) y
   `IdConverter`. Alternativa native-UUID requeriría rehacer C-8 y migración de datos (fuera
   de alcance).

---

## 13. Recomendación final

- **Modelo aprobado**: `orders`, `order_items`, `client` con PK `bigint`, FKs internas solo
  entre tablas propias (`orders→client`, `order_items→orders`), refs externas como columnas
  Long sin FK, índices y constraints según §8/§9.
- **Modelo que requiere decisión**: snapshot de producto en `order_items` (§12.1) —
  dependerá de si se prioriza autocontención (B) o lectura live (A).
- **Bloqueo**: `DeliveryInfo`/`route` en lectura carecen de contrato (§12.2) → pendiente
  hasta que Delivery exponga los endpoints de lectura.
