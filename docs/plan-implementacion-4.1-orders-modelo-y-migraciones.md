## 1. En pocas palabras

Hoy, cuando un cliente hace un pedido, el pedido nace como "Nuevo pedido" y la tienda lo ve al instante. **No se cobra nada**: el método de pago es solo una etiqueta.

Para vender con pago real, el pedido tiene que esperar a que el pago se confirme. Para eso la base de datos de orders necesita cuatro cosas nuevas:

1. **Un libro de pagos** (`payments`): qué se intentó cobrar, por cuánto y si salió bien.
2. **Datos nuevos en el pedido** (`orders`): un estado "Pendiente de pago", una llave anti-duplicados para que un doble toque en "Pagar" no cree dos pedidos, y dos relojes (plazo para pagar y plazo para que la tienda responda).
3. **Un libro de reembolsos** (`refunds`): cuando un pedido se cierra sin entrega, se devuelve el dinero (todo o la parte que corresponda). Cada devolución queda registrada con su estado y sus reintentos.
4. **Plazos configurables** (`order_policies`): cuánto tiempo hay para pagar, para que la tienda responda y para que el cliente cancele. Los define el administrador y cada tienda puede ajustar los suyos.

Este punto **solo prepara el terreno**: tablas, columnas y las clases del código que las representan. No cobra, no llama a ninguna pasarela y no cambia lo que ve el usuario. Eso viene en los puntos 4.2 a 4.5.

**Por qué conviene hacerlo primero y por separado:** es un cambio puramente aditivo (agrega, no quita ni modifica nada existente). Si algo sale mal, la versión actual de la app sigue funcionando sin enterarse.

**No hace falta decidir la pasarela para empezar.** El nombre del proveedor se guarda como texto, así que sirve igual para el modo demo (`fake`) que para Webpay, Mercado Pago o Flow.

## 3. Las cuatro migraciones

Orden de ejecución: `V6` → `V7` → `V8` → `V9`. Una migración por archivo, en
`services/orders-service/src/main/resources/db/migration/`.

### 3.1 `V6__payments.sql` — el libro de pagos

**En palabras simples.** Cada vez que se le pide dinero a un cliente por un pedido, se anota una fila: cuánto, a qué proveedor, y en qué va (pendiente, aprobado, rechazado, vencido). Un pedido puede tener varios intentos (el primero rechazado, el segundo aprobado), pero **nunca dos cobros aprobados**. Eso último lo garantiza la propia base de datos, no solo el código.

**Detalle técnico.**

```sql
CREATE TABLE public.payments (
  id             bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  order_id       bigint        NOT NULL,
  provider       varchar(30)   NOT NULL,                 -- fake | webpay | mercadopago | flow
  provider_tx_id varchar(100)  NOT NULL,
  amount         numeric(12,2) NOT NULL CHECK (amount > 0),
  currency       char(3)       NOT NULL DEFAULT 'CLP',
  status         varchar(12)   NOT NULL DEFAULT 'PENDIENTE',
  raw_status     varchar(100),                           -- estado tal cual lo informó la pasarela
  created_at     timestamptz   NOT NULL DEFAULT now(),
  updated_at     timestamptz   NOT NULL DEFAULT now(),
  CONSTRAINT fk_payments_order  FOREIGN KEY (order_id) REFERENCES public.orders(id) ON DELETE RESTRICT,
  CONSTRAINT chk_payments_status CHECK (status IN ('PENDIENTE','APROBADO','RECHAZADO','EXPIRADO')),
  CONSTRAINT uq_payments_provider_tx UNIQUE (provider, provider_tx_id)
);

CREATE INDEX idx_payments_order ON public.payments(order_id);
-- Seguros contra doble cobro: una sola transacción abierta y un solo pago aprobado por pedido.
CREATE UNIQUE INDEX uq_payments_one_pending  ON public.payments(order_id) WHERE status = 'PENDIENTE';
CREATE UNIQUE INDEX uq_payments_one_approved ON public.payments(order_id) WHERE status = 'APROBADO';
```

Decisiones y por qué:

- **`ON DELETE RESTRICT`** (los hijos actuales usan `CASCADE`): un registro de dinero no debe desaparecer por borrar un pedido. Hoy la eliminación de cuenta solo anonimiza direcciones y conserva los pedidos, así que no choca.
- **`UNIQUE (provider, provider_tx_id)`** en vez de solo `provider_tx_id` (la especificación dice "único"): dos pasarelas distintas podrían repetir un identificador. Es más estricto en la práctica y no cuesta nada.
- **Los dos índices parciales** no están en la especificación; son la protección real contra el doble cobro cuando llegan el webhook y el `PaymentExpirationJob` al mismo tiempo. El reintento de pago (`payment/retry`, P1) solo podrá crear una transacción nueva cuando la anterior ya no esté `PENDIENTE`.
- `CHECK` de estado en `payments` sí conviene (tabla nueva, sin historia). En `orders.status` **no** se agrega: ya hay filas y código que dependen de que sea texto libre.

### 3.2 `V7__order_payment_fields.sql` — los datos nuevos del pedido

**En palabras simples.** Al pedido se le agregan tres datos: la **llave anti-duplicados** (si la app reenvía la misma petición por mala señal, se devuelve el mismo pedido en vez de crear otro), el **plazo para pagar** (propuesta: 15 min) y el **plazo para que la tienda responda** (propuesta: 10 min). El estado "Pendiente de pago" también es parte de este cambio, pero vive en el código (ver §4).

Los pedidos que ya existen no se tocan: quedan sin llave y sin plazos, y siguen funcionando igual.

**Detalle técnico.**

```sql
ALTER TABLE public.orders
    ADD COLUMN IF NOT EXISTS idempotency_key        varchar(64),
    ADD COLUMN IF NOT EXISTS payment_expires_at     timestamptz,
    ADD COLUMN IF NOT EXISTS store_response_due_at  timestamptz;

-- Misma llave del mismo cliente = mismo pedido. Los NULL (pedidos históricos) no chocan entre sí.
CREATE UNIQUE INDEX IF NOT EXISTS uq_orders_client_idempotency
    ON public.orders(client_id, idempotency_key);

-- Soporte de las tareas programadas (4.4): solo indexan las filas que les interesan.
CREATE INDEX IF NOT EXISTS idx_orders_payment_expiry
    ON public.orders(payment_expires_at) WHERE status = 'Pendiente de pago';
CREATE INDEX IF NOT EXISTS idx_orders_store_response_due
    ON public.orders(store_response_due_at) WHERE status = 'Nuevo pedido';
```

Notas:

- `store_response_due_at` **se llena cuando el pago se aprueba** (el reloj de la tienda arranca ahí, no al crear el pedido). Esta migración solo crea la columna.
- No se cambia el `DEFAULT 'Nuevo pedido'` de `orders.status`. El caso de uso de creación fija el estado de forma explícita; cambiar el default tocaría el seed local (`migration_local/V1_1`) y no aporta.
- Opcional (no está en la especificación): guardar un hash del cuerpo de la petición junto a la llave, para responder 422 si alguien reutiliza la misma llave con otro contenido. Propongo dejarlo fuera de 4.1 y decidirlo en el PR de `POST /api/orders`.

### 3.3 `V8__refunds.sql` — el libro de reembolsos

**En palabras simples.** Cuando un pedido pagado se cierra sin entrega (la tienda lo rechaza, el cliente cancela, la tienda no responde, el repartidor no puede entregar), se devuelve el dinero. Cada devolución es una fila con su motivo, su estado y cuántas veces se intentó. Si falla, queda visible para Soporte en lugar de perderse.

**Detalle técnico.**

```sql
CREATE TABLE public.refunds (
  id                 bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  payment_id         bigint        NOT NULL,
  order_id           bigint        NOT NULL,
  amount             numeric(12,2) NOT NULL CHECK (amount > 0),
  reason             varchar(20)   NOT NULL,
  status             varchar(10)   NOT NULL DEFAULT 'PENDIENTE',
  attempts           integer       NOT NULL DEFAULT 0 CHECK (attempts >= 0),
  next_attempt_at    timestamptz,                       -- para la espera creciente de RefundRetryJob
  refund_key         varchar(64)   NOT NULL,            -- llave de idempotencia enviada a la pasarela
  provider_refund_id varchar(100),
  last_error         varchar(500),
  created_at         timestamptz   NOT NULL DEFAULT now(),
  updated_at         timestamptz   NOT NULL DEFAULT now(),
  CONSTRAINT fk_refunds_payment FOREIGN KEY (payment_id) REFERENCES public.payments(id) ON DELETE RESTRICT,
  CONSTRAINT fk_refunds_order   FOREIGN KEY (order_id)   REFERENCES public.orders(id)   ON DELETE RESTRICT,
  CONSTRAINT chk_refunds_reason CHECK (reason IN
      ('RECHAZO','CANCELACION','VENCIMIENTO','F17','F18','CLIENTE_AUSENTE')),
  CONSTRAINT chk_refunds_status CHECK (status IN ('PENDIENTE','HECHO','FALLIDO')),
  CONSTRAINT uq_refunds_key     UNIQUE (refund_key)
);

CREATE INDEX idx_refunds_order ON public.refunds(order_id);
CREATE UNIQUE INDEX uq_refunds_one_total ON public.refunds(payment_id) WHERE refund_type = 'TOTAL';
CREATE INDEX idx_refunds_retry ON public.refunds(status, next_attempt_at) WHERE status <> 'HECHO';
```

> **Actualización (decisión del equipo):** el reembolso es **paramétrico: total o parcial**
> (`refund_type`). Un pago puede tener varios reembolsos parciales y como máximo uno total. Que la
> suma devuelta no supere lo cobrado lo valida el dominio (`Refund.open`), porque depende del monto
> del pago, que está en otra tabla.

Diferencias respecto de la especificación:

| Agregado | Para qué |
|---|---|
| `refund_type` (TOTAL / PARCIAL) | Decisión del equipo: según el caso se devuelve todo o la parte que corresponda. |
| `next_attempt_at` | La especificación pide "espera creciente" entre reintentos; sin esta columna no hay dónde guardarla. |
| `refund_key` único | `PaymentGateway.refund(...)` recibe un `refundKey` (sección 4.2): debe persistirse para reintentar sin devolver dos veces. |
| Índice parcial `uq_refunds_one_total` | Impide dos reembolsos totales del mismo pago, pero permite varios parciales. |
| Valor `CLIENTE_AUSENTE` | Está en la especificación; su regla de monto ahora se resuelve con reembolso parcial. |

### 3.4 `V9__order_policies.sql` — los plazos configurables (nuevo)

**En palabras simples.** Los tiempos del pedido ya no son números fijos dentro del programa: los
define el administrador (valores para toda la plataforma) y cada tienda puede ajustar los suyos.
Hay tres:

| Plazo | Qué significa | Valor inicial |
|---|---|---|
| Para pagar | Cuánto tiempo tiene el cliente para pagar antes de que el pedido venza | 15 min |
| Respuesta de la tienda | Cuánto tiempo tiene la tienda para aceptar un pedido ya pagado | 10 min |
| Cancelación del cliente | Minutos desde la compra en que el cliente aún puede cancelar. **0 = no puede cancelar.** Pasado ese plazo, o una vez que el producto salió de la tienda, el pedido se cobra igual | 5 min |

Si una tienda no configura un plazo, usa el de la plataforma. Cada campo se hereda por separado
(una tienda puede cambiar solo el plazo de respuesta y seguir con los demás valores globales).

**Detalle técnico.** Tabla `order_policies`: una fila global (`restaurant_id IS NULL`, con los tres
valores obligatorios y sembrada por la migración) y, opcionalmente, una fila por tienda con campos
nulos que heredan. Rangos 1 a 1440 minutos (0 permitido en cancelación), validados en la base y en
el dominio. `OrderPolicyResolver.effectiveFor(restaurantId)` entrega los valores ya resueltos. Los
endpoints para que el admin y el dueño los editen son un cambio posterior (4.3+); en 4.1 queda el
modelo, la persistencia y la resolución.

## 4. Cambios en el código Java (la otra mitad de "modelo")

**En palabras simples.** Las tablas solas no hacen nada: hay que enseñarle al servicio que existen. Y, sobre todo, hay que asegurarse de que **un pedido sin pagar sea invisible** para la tienda y para los repartidores. Si se nos escapa un solo lugar, una tienda podría preparar un pedido que nadie pagó.

### 4.1 Estado nuevo

`OrderStatus` (`domain/model/OrderStatus.java`): agregar `PENDIENTE_PAGO("Pendiente de pago")`.

Transiciones nuevas en `Order.VALID_TRANSITIONS` (mapa en `domain/model/Order.java`):

| Desde | Hacia | Quién lo dispara |
|---|---|---|
| Pendiente de pago | Nuevo pedido | Sistema (webhook de pago aprobado) — **no** un usuario por la API |
| Pendiente de pago | Cancelado | Cliente, o el sistema al vencer el plazo / pago rechazado |

`RoleTransitionPolicy`: la tienda y el repartidor **no** pueden mover un pedido que esté en Pendiente de pago; el cliente solo puede cancelarlo.

### 4.2 Lugares que hoy dejarían pasar un pedido sin pagar (revisados en `main`)

| # | Dónde | Hallazgo | Qué hacer |
|---|---|---|---|
| 1 | `Order.isClaimable()` | Usa `!status.isClosed()`. Como `PENDIENTE_PAGO` no estaría "cerrado", **un repartidor podría tomar un pedido sin pagar** | Excluir `PENDIENTE_PAGO` explícitamente (y decidir si `isClosed()` debe incluirlo o si se crea un método propio como `isPendingPayment()`) |
| 2 | `JpaOrderRepositoryAdapter.findAll(restaurantId)` | Devuelve **todos** los estados del local; `ListOrdersUseCase` lo usa para el rol Restaurante | Nuevo método del puerto que excluya `PENDIENTE_PAGO` para la vista de tienda. El cliente sí debe ver su pedido pendiente |
| 3 | `GetOrderDetailUseCase` y `InternalOrdersController` | Permiten leer un pedido por id | Verificar que tienda y delivery no obtengan un pedido en Pendiente de pago (404 o 403) |
| 4 | `TERMINAL_STATUSES` (conteos de pedidos activos) | `Pendiente de pago` contaría como "activo" para cliente, tienda y repartidor | Para la tienda y el repartidor no debe contar. Para el cliente (bloqueo de eliminar cuenta, 4.5) se decide aparte |
| 5 | `available-for-delivery` | Ya filtra por `LISTO_PARA_RETIRO`: **no requiere cambio**, solo una prueba que lo demuestre | Agregar la prueba |
| 6 | `sales-summary` | Ya cuenta solo `ENTREGADO`: **sin cambio en 4.1** (el descuento de reembolsos es 4.5) | — |
| 7 | `SupabaseRestOrderRepositoryAdapter` | Segunda implementación de `OrderRepositoryPort` (perfil `supabase`). Si se agregan métodos al puerto, **también hay que implementarlos aquí** o no compila | Implementar o lanzar `UnsupportedOperationException` documentado, según se siga usando ese perfil |
| 8 | Apps (Flutter y web) | `OrderStatus.fromValue` lanza error con estados desconocidos, y las apps antiguas podrían fallar al recibir "Pendiente de pago" | Avisar en el PR; está cubierto en las secciones 9 y 10 de la especificación |

## 6. Qué probar

**Migración** (con `PostgresIntegrationTestSupport`; en esta máquina Testcontainers con Docker Engine 29 necesita el ajuste de `~/.docker-java.properties`):

1. Base vacía → `V1` a `V8` aplican en orden sin error.
2. Base con pedidos creados con `V1` a `V5` (cargar antes de migrar) → después de `V8` los pedidos siguen legibles, con `idempotency_key` y plazos nulos.
3. Dos pedidos del mismo cliente con la misma llave → el segundo falla; misma llave en clientes distintos → pasa; dos pedidos con llave nula → pasan.
4. Un pago `APROBADO` y otro `APROBADO` para el mismo pedido → el segundo falla. Dos `PENDIENTE` → falla. Uno `RECHAZADO` y luego uno `PENDIENTE` → pasa.
5. Mismo `(provider, provider_tx_id)` dos veces → falla.
6. Estado o motivo fuera de la lista, o monto ≤ 0 → falla.
7. Dos reembolsos para el mismo pago → falla.
8. Borrar un pedido con pago → falla (`RESTRICT`).

**Dominio y consultas** (una por cada fila de §4.2): el repartidor no puede tomar un pedido sin pagar; la tienda no lo lista; el cliente sí; `available-for-delivery` no lo devuelve; la tienda no puede cambiarle el estado.

**Regresión:** `OrderControllerStatusAuthzIT` y el resto de la suite existente deben seguir verdes sin modificarlas.

## 7. Despliegue y marcha atrás

**En palabras simples.** Como solo se agregan cosas, la versión anterior sigue funcionando aunque las tablas nuevas existan. El único cuidado: si algún día volvemos atrás **después** de que existan pedidos "Pendiente de pago", la versión vieja no sabría leerlos.

- El deploy aplica `V6` a `V8` con la CLI de Flyway **antes** de levantar la versión nueva y verifica `flyway_schema_history`. Si falta alguna, hace rollback de la aplicación (pero las migraciones ya aplicadas quedan). Por eso deben ser siempre compatibles hacia atrás, como estas.
- **Respaldo previo** de la base de orders antes del primer despliegue (la especificación lo pide).
- **No activar el flujo de pago en el mismo despliegue.** Mientras `POST /api/orders` siga creando pedidos en "Nuevo pedido" (hasta el paso 3 del orden de implementación), no existirá ningún pedido pendiente y la marcha atrás es trivial.
- Si el rollback fuera necesario con pedidos pendientes: cancelarlos antes (`UPDATE … SET status='Cancelado' WHERE status='Pendiente de pago'`) y liberar su reserva de stock.

## 8. Decisiones tomadas, observaciones y pendientes

### 8.1 Decisiones del equipo (ya incorporadas en 4.1)

| # | Decisión | Dónde quedó |
|---|---|---|
| 1 | **Reembolso paramétrico: total o parcial.** Según el caso se devuelve todo o la parte que corresponda | `refunds.refund_type`; regla de suma en `Refund.open` |
| 2 | **Cancelación del cliente:** no se puede cancelar una vez que el producto salió de la tienda (se cobra igual). Antes, el cliente tiene un plazo desde la compra, y **lo define la tienda** | `order_policies.customer_cancel_window_minutes` (0 = no cancelable). El bloqueo post-retiro ya existe en el flujo de estados; aplicar la ventana es del PR de cancelación (4.3) |
| 3 | **Protección contra doble cobro:** aprobada, y debe quedar explícita en el PR por ser un tema de seguridad | Índices `uq_payments_one_pending` y `uq_payments_one_approved` |
| 4 | **Datos adicionales** (`refund_key`, `next_attempt_at`, `provider + tx` único): quedan; los datos de la ficha de producto, etc. se dejan pendientes | V6 y V8 |
| 5 | **Supabase se mantiene** (mejor que sobre): el adaptador legacy también filtra los pedidos sin pagar y excluye pendientes de los conteos de tienda y repartidor; lo que no aplica a ese perfil (pagos, idempotencia) lanza un error explícito, igual que la entrega con código | `SupabaseRestOrderRepositoryAdapter` |
| 6 | **Plazos paramétricos:** pagar, respuesta de la tienda y cancelación los define el admin (global) o el dueño (su tienda). No son variables de entorno | V9 + `OrderPolicyResolver` |

> Cambio respecto de la especificación: `PAYMENT_EXPIRATION_MINUTES` y `STORE_RESPONSE_MINUTES`
> (sección 12) dejan de ser variables de entorno; son los valores globales de `order_policies`.

### 8.2 Observaciones (no bloquean el desarrollo actual)

| # | Tema | Observación |
|---|---|---|
| 4 | **Apps y web** | Aparece el estado "Pendiente de pago". Las apps antiguas podrían fallar al recibirlo. El cobro no se activa hasta que Flutter y la web lo soporten. 4.1 no cambia nada visible, así que no hay riesgo todavía |
| 5 | **Pedidos históricos sin pago** | Los pedidos ya entregados nunca pasaron por una pasarela y no se les crean pagos retroactivos. Cuando `sales-summary` pase a "solo pagados" (4.5) hay que decidir cómo se cuentan |
| 6 | **Cuenta con pedido sin pagar** | Hoy un pedido pendiente cuenta como "en curso" para el cliente (bloquea eliminar la cuenta) pero no para la tienda ni el repartidor. Vence solo con el plazo de pago; se confirma en 4.5 |
| — | **Reintento de pago** | El índice "un solo pago abierto por pedido" no admite dos `PENDIENTE` ni por un instante: el código de reintento (4.3) debe cerrar el intento anterior y confirmarlo en la base antes de abrir el siguiente (la prueba `paymentsOfAnOrderComeNewestFirst` lo muestra) |
| — | **Quién edita los plazos** | Falta el endpoint para el admin y el dueño. Debe validar que el dueño solo toque su tienda y definir si hay topes para lo que puede fijar un dueño (por ejemplo, que no ponga 1 minuto de respuesta). Va con 4.3 |
