# Base de datos de auth-service

El esquema y los datos de desarrollo **los aplica Flyway al arrancar el
servicio**, desde `src/main/resources/db/migration/`:

| Migración | Qué hace |
|---|---|
| `V1__create_schema.sql` | Crea `users`, `login`, `roles`, `user_has_roles`, `refresh_tokens` |
| `V2__seed_development.sql` | Carga los usuarios y roles demo con IDs fijos |

No hay que ejecutar SQL a mano ni hace falta un editor: basta con levantar el
servicio apuntando a una base vacía.

> Los scripts sueltos que vivían en esta carpeta se eliminaron al migrar a
> Flyway. Mantener dos copias del mismo DDL garantizaba que tarde o temprano
> divergieran.

## Los IDs del seed no se tocan

Al separar las bases desaparecieron las claves foráneas entre servicios. Estos
usuarios son referenciados por los seeds de los otros tres y Postgres ya no
puede validarlo:

| ID | Email | Quién lo referencia |
|---|---|---|
| 1 | cliente@demo.cl | Orders → `client.user_id = 1` |
| 2 | restaurante@demo.cl | Catalog → `restaurant.user_id = 2` |
| 3 | repartidor@demo.cl | Delivery → `delivery.user_id = 3` |
| 4 | admin@demo.cl | Orders y Delivery (multirol) |
| 5 | araucomaipu@flashdrop.cl | Catalog → `restaurant.user_id = 5` |

Si cambian, el flujo end-to-end falla con errores de "usuario no encontrado"
que no apuntan a la causa. Cualquier cambio hay que coordinarlo con Felipe,
Javier y Sebastián.

## Por qué el seed sincroniza las secuencias

Las tablas son `generated by default as identity`. Los `INSERT` con id
explícito **no** avanzan la secuencia, así que sin el bloque `setval` del final
el primer `POST /auth/register` intentaría insertar `id = 1` y fallaría con
`23505 duplicate key`.

## Verificar

```sql
select table_name from information_schema.tables
 where table_schema = 'public' order by 1;
```

Deben estar las cinco tablas más `flyway_schema_history`, y ninguna de otro
servicio.
