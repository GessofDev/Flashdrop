# Base de datos de auth-service

Esquema y seed de la base **independiente** de auth-service
(MIGRATION_PLAN.pdf §4.1 y Fase 3).

| Archivo | Qué hace |
|---|---|
| `01_schema.sql` | Crea `users`, `login`, `roles`, `user_has_roles`, `refresh_tokens` |
| `02_seed.sql` | Carga los usuarios y roles demo con IDs fijos |

Ninguna otra tabla del sistema vive aquí. `client`, `restaurant`, `delivery`,
`orders`, `order_items`, `categories`, `products` y `delivery_routes` son de
otros servicios y se consultan por HTTP, nunca por SQL.

## Aplicar

Contra el proyecto Supabase de auth (Studio → SQL Editor), o por psql:

```bash
psql "$AUTH_DB_URL" -f auth-service/db/01_schema.sql
```

```bash
psql "$AUTH_DB_URL" -f auth-service/db/02_seed.sql
```

`01_schema.sql` hace `drop table ... cascade` al inicio: **borra los datos**.
Es lo esperado en esta etapa (el PDF dice que no hay producción), pero no lo
corras sobre una base que quieras conservar. `02_seed.sql` sí es idempotente
(`on conflict do nothing`).

## Los IDs del seed no se tocan

Al separar las bases desaparecen las FK entre servicios. Estos usuarios son
referenciados por los seeds de los otros tres y Postgres ya no puede
validarlo:

| ID | Email | Quién lo referencia |
|---|---|---|
| 1 | cliente@demo.cl | Orders → `client.user_id = 1` |
| 2 | restaurante@demo.cl | Catalog → `restaurant.user_id = 2` |
| 3 | repartidor@demo.cl | Delivery → `delivery.user_id = 3` |
| 4 | admin@demo.cl | Orders y Delivery (multirol) |
| 5 | araucomaipu@flashdrop.cl | Catalog → `restaurant.user_id = 5` |

Si cambian, el flujo end-to-end de la Fase 4 falla con errores de "usuario no
encontrado" que no apuntan a la causa real. Cualquier cambio hay que
coordinarlo con Felipe, Javier y Sebastián.

## Por qué el seed resetea las secuencias

Las tablas son `generated by default as identity`. Los `INSERT` con id
explícito del seed **no** avanzan la secuencia, así que sin el bloque de
`setval` del final el primer `POST /auth/register` intentaría insertar `id = 1`
y fallaría con `23505 duplicate key`.

## RLS

El esquema habilita Row Level Security en las cinco tablas y **no** define
ninguna política. auth-service entra con la `service_role` key, que hace
bypass de RLS; cualquier otra clave (`anon`, `authenticated`) queda sin
acceso. Es lo que impide que la app móvil lea la tabla `login` directamente
por PostgREST.
