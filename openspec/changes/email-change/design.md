# Design: `email-change`

## 1. Arquitectura y decisiones de diseño

El flujo reutiliza el patrón exacto de `RequestPasswordResetService` + `ResetPasswordService` en `auth-service`, adaptado a las 3 decisiones de producto:

1. **Link solo al email actual**: la tabla `email_change_tokens` no necesita columna `pending_email`, porque el usuario envía `newEmail` en el paso de confirmación (`POST /auth/email/confirm`). Esto mantiene el esquema mínimo y evita almacenar correos no confirmados.
2. **Re-autenticación con contraseña en la solicitud**: `POST /auth/email/change-request` exige JWT válido y contraseña actual antes de emitir el token y enviar el correo.
3. **Revocación total de sesiones**: al confirmar, `RefreshTokenStore.revokeAllForUser(userId)` invalida todos los refresh tokens activos. Los access tokens RS256 ya emitidos son stateless y expiran naturalmente en 15 minutos (`JwtTokenService`).

## 2. Esquema de base de datos (Flyway)

Nueva migración `services/auth-service/src/main/resources/db/migration/V6__create_email_change_tokens.sql`:

```sql
create table public.email_change_tokens (
  id         bigint generated by default as identity primary key,
  user_id    bigint      not null references public.users(id) on delete cascade,
  token_hash text        not null unique,
  expires_at timestamptz not null,
  used_at    timestamptz,
  created_at timestamptz not null default now()
);

create index idx_email_change_tokens_user on public.email_change_tokens (user_id);
```

## 3. Modelo de dominio y puertos

### 3.1 Dominio (`com.flashdrop.auth.domain`)
- `User.conEmail(Email newEmail)`: retorna una nueva instancia de `User` preservando `id`, `rut`, `name`, `lastName`, `phone`, `photo`, `roles`, `createdAt`.
- `EmailChangeToken` (record análogo a `PasswordResetToken`): `(Long userId, String tokenHash, Instant expiresAt)`.
- Excepciones de dominio:
  - `EmailAlreadyExistsException` (ya existe en el dominio para registro; mapear a `409` con `EMAIL_ALREADY_EXISTS`).
  - `InvalidEmailChangeTokenException` (mapear a `400`/`401` igual que `InvalidResetTokenException`).

### 3.2 Puertos inbound (`application/port/inbound`)
- `RequestEmailChangeUseCase`: `void requestChange(RequestEmailChangeCommand command)`
- `ConfirmEmailChangeUseCase`: `void confirmChange(ConfirmEmailChangeCommand command)`

### 3.3 Puertos outbound (`application/port/outbound`)
- `CredentialStore`: agregar `void updateLogin(Long userId, String newLogin)` y `boolean existsByLogin(String login)`.
- `EmailChangeTokenStore`:
  - `void save(EmailChangeToken token)`
  - `Optional<Long> consume(String tokenHash, Instant now)`
  - `void invalidateAllForUser(Long userId, Instant now)`
- `EmailChangeMailer`:
  - `void sendConfirmationLink(String currentEmail, String name, String link, Duration ttl)`
  - `void sendEmailChangedNotice(String newEmail, String name)` *(aviso informativo sin enlace)*
- `TransactionalRunner` (o adaptador de transacción en infraestructura): ejecuta el bloque de confirmación dentro de una transacción única sin filtrar `@Transactional` hacia `application/`.

## 4. Transaccionalidad y manejo de concurrencia

Para cumplir **NFR-1** (cero imports de Spring en `application/`) y **NFR-2** (atomicidad):

- `TransactionalRunner` es un port de `application/port/outbound`. Su implementación `SpringTransactionalRunner` (en `infrastructure/`) usa un `PlatformTransactionManager` y **falla de forma explícita** si no hay ninguno: ejecutar el bloque sin transaccion dejaria `users.email` y `login.login` able de divergir. No hay fallback silencioso (`AGENTS.md` §4).
- En `ConfirmEmailChangeService`:
  1. Valida `Email` (`newEmail`) y rate limit **antes** de abrir la transaccion o consumir el token.
  2. **El token se valida antes de mirar el email destino.** El chequeo de colision vive dentro de la transaccion, despues de consumir el token. Si el chequeo estuviera antes, un llamador sin sesion distinguiria "ese email existe" (409) de "no existe" (400) y enumeraria las cuentas registradas.
  3. Dentro del `TransactionalRunner.run(...)`:
     - Consume el token (`emailChangeTokens.consume(hash, now)`). Es el primer paso: si el token no sirve, no se toca nada mas.
     - Verifica que la cuenta siga activa (`credentials.isActive(userId)`).
     - Verifica colision (`users.existsByEmail(newEmail) || credentials.existsByLogin(newEmail.value())`). La excepcion hace rollback, asi que **el token no queda consumido** y el usuario puede reintentar con otro email.
     - Actualiza `users.email` con un UPDATE dirigido a esa columna (`users.updateEmail(userId, newEmail)`): no se reescribe la fila completa, asi que un perfil editado en paralelo no se pisa.
     - Actualiza `login.login` (`credentials.updateLogin(userId, newEmail.value())`). `updateLogin` falla si no afecta filas, para que no pueda quedar un email nuevo con un login viejo.
     - Revoca refresh tokens (`refreshTokens.revokeAllForUser(userId)`).
     - Invalida tokens de cambio pendientes (`emailChangeTokens.invalidateAllForUser(userId, now)`).
  4. Si ocurre una colision concurrente en BD (`UNIQUE` en `users.email` o `login.login`), la transaccion hace rollback completo (el token no queda marcado como usado). La capa de infraestructura traduce el fallo de persistencia a `ResourceAlreadyExistsException` y el caso de uso la convierte en `EmailAlreadyInUseException`, de modo que el cliente recibe siempre `409` con `code="EMAIL_ALREADY_EXISTS"`.

## 4.2 Identidad de la IP del cliente

El gateway **agrega** el peer real al final de `X-Forwarded-For` y publica `x-real-ip` sobrescribiendo el valor del cliente. Los endpoints del flujo de cambio de email resuelven la IP con `x-real-ip`, y si no esta, con el **ultimo** salto de `X-Forwarded-For` (nunca el primero): tomar el primer salto deja que cualquiera rote el encabezado y se escape del limite por IP.

Los demas endpoints de `auth-service` siguen usando el primer salto. Corregir el limite y la auditoria del login y del resto de flujos es un cambio aparte, con su propio analisis de regresion.

## 4.1 Rate limiting

- `POST /auth/email/change-request` cuenta **cada** intento contra el limite por `userId` y por IP, validos e invalidos: cada solicitud puede poner un correo en la via, asi que una solicitud correcta tampoco es gratis. Es el mismo criterio que usa `RequestPasswordResetService`.
- `POST /auth/email/confirm` cuenta cada intento contra el limite por IP.

## 5. Seguridad y Gateway

- **Spring Security (`SecurityConfig.java`)**: `POST /auth/email/change-request` y `POST /auth/email/confirm` deben figurar en `.permitAll()`, ya que el `SecurityFilterChain` termina en `anyRequest().denyAll()` y la validación del JWT en `/change-request` se hace explícitamente en `AuthController` con `validateToken.validate(bearer(authorization))`.
- **Gateway (`gateway/docker/gateway.yaml`)**: agregar `/auth/email/confirm` en `jwtOverrides` con `jwt.enabled: false`. El prefijo `/auth` ya enruta hacia `auth-service:8081`.
- **Arranque**: `EmailChangeConfig` **no** aborta el arranque si falta `EMAIL_CHANGE_URL` o el SMTP. Un despliegue con SMTP habilitado pero sin la URL nueva perderia el servicio entero de `auth-service`; el flujo de cambio de email queda sin correo y lo avisa en el log. `EMAIL_CHANGE_URL` se cablea en `docker-compose.stack.yml` y `env.stack.template`.
- **Schema estricto**: Spring Boot desactiva globalmente `FAIL_ON_UNKNOWN_PROPERTIES`, asi que `@JsonIgnoreProperties(ignoreUnknown = false)` no alcanza. Los DTOs del flujo usan `@JsonAnySetter` para rechazar campos desconocidos con `400`.
