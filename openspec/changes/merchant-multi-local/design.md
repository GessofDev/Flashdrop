# Design: `merchant-multi-local`

## 1. Arquitectura

```
apps/web (React) / apps Flutter (tienda)
   │  GET  /api/catalog/my/restaurants          → lista de locales del merchant
   │  GET  /api/catalog/my/restaurant           → local activo (compat)
   │  X-My-Store-Restaurant: <restaurantId>     → contexto de local por request
   ▼
gateway (Fastify) ── /api/catalog ──►  catalog-service
                                          │  owns merchants, merchant_members,
                                          │       restaurant, products, hours
                                          ▼
   orders-service ── GET /api/internal/owner/restaurants?userId=  (X-Internal-Api-Key)
   reviews-service ─ GET /api/internal/owner/restaurants?userId=  (X-Internal-Api-Key)
```

La frontera de servicio **no cambia**: `catalog-service` sigue siendo el dueño
exclusivo del dominio de comercio. `merchant` no es un servicio nuevo, es una
entidad nueva dentro del servicio que ya posee la ficha del local.

### 1.1 Por qué `merchant` y no "N:M usuario↔restaurante"

El modelo barato (quitar el `UNIQUE`, permitir N restaurantes por `user_id`)
resuelve el caso inmediato, pero deja la propiedad sin dueño semántico:

- No hay entidad que represente "la marca": el nombre comercial, el teléfono
  de contacto y el estado operativo del grupo.
- No hay forma de agregar un segundo operador al grupo más adelante sin volver
  a migrar.
- La pregunta "¿qué es una tienda?" queda respondida por el `user_id` de
  auth, que es un usuario de personas, no una organización.

`merchant` da un lugar donde colgar todo eso más adelante sin romper nada.

### 1.2 El path feliz del cliente no se toca

`POST /api/orders` **no** lleva `restaurantId`: el cliente manda
`items: [{productId, quantity}]` y `CreateOrderUseCase.java:88-103` deriva el
restaurante de los productos, exigiendo que todos los items pertenezcan al
mismo local (`Order.validateSingleRestaurant`). El `restaurant_id` de la orden
sale de ahí (`CreateOrderUseCase.java:166`).

Consecuencia: **el marketplace y el flujo de pedido son idénticos con un local
o con diez**. El cliente sigue eligiendo un local concreto en la UI (que ya
filtra por `restaurantId` en `GET /catalog/products?categoryId=&restaurantId=`,
`ProductController.java:62-71`) y pide contra ese. Multi-local no requiere
cambiar el contrato de pedidos.

## 2. Modelo de datos

Migraciones nuevas en `services/catalog-service/src/main/resources/db/migration/`.

### 2.1 `merchants`

```sql
create table public.merchants (
    id          bigint generated by default as identity primary key,
    name        varchar(255) not null,
    legal_name  varchar(255),
    tax_id      varchar(64),
    phone       varchar(32),
    email       varchar(255),
    status      varchar(16) not null default 'ACTIVO',
    created_at  timestamp(6) not null default current_timestamp,
    updated_at  timestamp(6) not null default current_timestamp
);
create index idx_merchants_name on public.merchants(name);
```

`merchant` es la **marca**: los datos que son de la marca y no del local.
`name` es el nombre comercial que el cliente ve; `legal_name` / `tax_id` son
opcionales y no se exponen en el marketplace.

### 2.2 `merchant_members`

```sql
create table public.merchant_members (
    id          bigint generated by default as identity primary key,
    merchant_id bigint not null references public.merchants(id) on delete cascade,
    user_id     bigint not null,
    role        varchar(16) not null default 'DUEÑO',
    created_at  timestamp(6) not null default current_timestamp,
    constraint uq_merchant_member unique (merchant_id, user_id)
);
create index idx_merchant_members_user on public.merchant_members(user_id);
```

- **Sin FK a `users`**: `catalog-service` no es dueño de la base de `auth`
  (AGENTS.md §2 — cada servicio es dueño de sus tablas y de su usuario de
  base). `user_id` es una referencia lógica, igual que `restaurant.user_id` lo
  es hoy.
- **`role`**: `DUEÑO` | `ENCARGADO`. Ambos acceden a los locales del merchant;
  la diferencia de permisos queda para una fase posterior (fuera de alcance,
  §6 de la proposal).
- **`on delete cascade`**: si se borra el merchant, se van sus miembros.

### 2.3 `restaurant.merchant_id`

```sql
alter table public.restaurant
    add column merchant_id bigint references public.merchants(id) on delete restrict;
create index idx_restaurant_merchant on public.restaurant(merchant_id);
```

`merchant_id` es **nullable** en la primera fase: los restaurantes creados por
el admin sin dueño siguen siendo válidos, y el backfill convive con el
`user_id` actual durante las fases 1 y 2.

`on delete restrict` (y no `cascade`) es deliberado: borrar una marca no
debe borrar locales con historial de pedidos. El borrado de un merchant exige
desvincular sus locales explícitamente.

### 2.4 Estado final de `restaurant`

```sql
-- restaurant.id            : id del local (sigue siendo la identidad operativa)
-- restaurant.merchant_id   : marca a la que pertenece (nullable hasta fase 3)
-- restaurant.user_id       : dueño legacy, se deprecia en fase 4
```

`restaurant` conserva su `id` público. **No hay migración de ids**: los
pedidos, las reseñas y las rutas de reparto apuntan a `restaurant.id` y no se
tocan.

### 2.5 Reparto de bases (no cambia)

| Base | Dueño | Tablas |
|---|---|---|
| `flashdrop_auth` | `auth_app` | `users`, `roles`, `user_has_roles`, `refresh_tokens`, … |
| `flashdrop_catalog` | `catalog_app` | `categories`, `restaurant`, `products`, `restaurant_hours`, `restaurant_rating_stats`, **`merchants`, `merchant_members`** (nuevas) |
| `flashdrop_orders` | `orders_app` | `orders`, `order_items`, `payments`, `order_policies`, … |
| `delivery_db` | `delivery_svc` | `delivery_routes`, `courier_positions`, `delivery_events` |
| `reviews_db` | `reviews_app` | `reviews` |

`merchants` y `merchant_members` nacen en `flashdrop_catalog`: el comercio es
dominio de catalog. `auth-service` no se toca.

## 3. Migraciones y backfill

Las migraciones son **aditivas y reversibles** hasta la fase 3.

### V11 — `merchants`

Crea `merchants` y `merchant_members` (secciones 2.1 y 2.2). No toca
`restaurant`.

### V12 — `restaurant.merchant_id`

Agrega la columna nullable y el índice (sección 2.3).

### V13 — backfill

Para cada `restaurant` con `user_id` no nulo:

1. Si el usuario ya tiene un merchant (`merchant_members` con `role='DUEÑO'`),
   se le asigna ese merchant.
2. Si no, se crea un merchant con `name` = nombre del restaurante (el nombre
   de la marca inicial es el del primer local) y se inserta el
   `merchant_member`.
3. Se setea `restaurant.merchant_id`.

```sql
insert into public.merchants (name)
select r.name
from public.restaurant r
where r.user_id is not null
  and not exists (select 1 from public.merchant_members mm where mm.user_id = r.user_id)
group by r.name;

insert into public.merchant_members (merchant_id, user_id, role)
select m.id, r.user_id, 'DUEÑO'
from public.restaurant r
join public.merchants m on m.name = r.name
where r.user_id is not null
group by m.id, r.user_id;

update public.restaurant r
set merchant_id = mm.merchant_id
from public.merchant_members mm
where mm.user_id = r.user_id and r.merchant_id is null;
```

El backfill es **1:1 con el estado actual**: un usuario con un restaurante
produce un merchant con un local. No hay pérdida de información y no cambia
el comportamiento de ninguna pantalla.

> Nota de implementación: el backfill agrupa por nombre de restaurante, así
> que dos franchises homónimas de dueños distintos caen en el mismo merchant
> (lo que es semánticamente correcto) y el nombre del merchant es el del
> primer local. Por eso `merchants.name` **no** es `unique`: dos marcas con el
> mismo nombre comercial son legales.

### V14 — quitar el `UNIQUE(user_id)` (fase 3)

```sql
alter table public.restaurant drop constraint restaurant_user_id_key;
```

Este es el **único punto irreversible** de todo el change. Va después de que
la fase 2 esté completa y verificada en producción.

## 4. Estrategia de rollout

| Fase | Qué pasa | Reversible |
|---|---|---|
| 1 | `merchants`, `merchant_members`, `restaurant.merchant_id`, backfill. Nada cambia para el cliente. | Sí (drop de tablas y columna) |
| 2 | Dual-write y dual-read: los endpoints de dueño resuelven por `merchant_member` con fallback a `user_id`. | Sí |
| 3 | Se elimina el `UNIQUE(user_id)`. La lectura de "mi local" pasa a ser por merchant. | **No** |
| 4 | Se deprecia `restaurant.user_id` cuando ningún consumidor lo lea. | Sí |

Las fases 1 y 2 pueden convivir con el modelo actual sin tocar el frontend.
La fase 3 requiere que el panel de dueño ya sepa mostrar una lista de locales.

## 5. Contratos

### 5.1 Público (no cambia)

| Endpoint | Efecto |
|---|---|
| `GET /catalog/restaurants?latitude=&longitude=` (`RestaurantController.java:34-55`) | Sigue devolviendo locales abiertos. **Cada local es una fila.** Con dos locales de la misma marca aparecen dos entradas, que es lo correcto: el cliente elige un local. El nombre visible se arma como **"marca — sucursal"** (Q1 cerrado): `RestaurantResponse` suma `merchantName` y el `name` del local queda siendo el nombre de la sucursal. |
| `GET /catalog/products?categoryId=&restaurantId=` (`ProductController.java:62-71`) | Sin cambios. |

### 5.2 De dueño (nuevos + compatibilidad)

El contexto de local viaja en el header **`X-My-Store-Restaurant`** (id del
local). Regla de resolución:

1. Si el header viene, se valida que el local pertenezca a un merchant del
   usuario → si no, `403`.
2. Si no viene y el usuario tiene **un** local → ese local (compatibilidad
   total con el comportamiento actual).
3. Si no viene y el usuario tiene **varios** locales → `400`
   `LOCAL_CONTEXT_REQUIRED` con la lista de locales disponibles.

| Endpoint | Nuevo/Existente | Descripción |
|---|---|---|
| `GET /api/catalog/my/restaurants` | **Nuevo** | Locales del merchant del usuario. `List<RestaurantResponse>`. Es el endpoint que habilita la UX multi-local. |
| `GET /api/catalog/my/merchant` | **Nuevo** | Ficha de la marca: nombre comercial, contacto, estado. |
| `POST /api/catalog/my/restaurants` | **Nuevo** | Crear un local dentro del merchant (sólo `DUEÑO`). Recibe nombre, dirección, coordenadas, radio. |
| `GET /api/catalog/my/restaurant` | Existente | Devuelve el local resuelto por el header. Mantiene la ruta y la forma de respuesta. |
| `PUT /api/catalog/my/restaurant/open-status` | Existente | Idem, sobre el local resuelto. |
| `PUT /api/catalog/my/restaurant/hours` | Existente | Idem. |
| `PUT /api/catalog/my/restaurant/location` | Existente | Idem. |
| `PUT /api/catalog/my/restaurant/delivery-radius` | Existente | Idem. |
| `GET /api/catalog/my/products` | Existente | Productos **del local resuelto**, no de todos. |
| `POST /api/catalog/my/products` | Existente | El producto se crea en el local resuelto. |
| `PUT /api/catalog/my/products/{productId}` | Existente | Valida que el producto pertenezca al local resuelto. |
| `DELETE /api/catalog/my/products/{productId}` | Existente | Idem. |

Los use cases que hoy resuelven el local por `userId`
(`GetRestaurantByUserIdUseCase.java:18-22`, `SetStoreOpenStatusUseCase.java:27`,
`SetStoreHoursUseCase.java:31`, `SetStoreLocationUseCase.java:27`,
`SetStoreDeliveryRadiusUseCase.java:24`, `OwnerCreateProductUseCase.java:44`,
`OwnerListProductsUseCase.java:31`, `OwnerUpdateProductUseCase.java:54`,
`OwnerDeleteProductUseCase.java:51`) cambian su firma para recibir el
`restaurantId` ya resuelto. La resolución del contexto pasa a un
`StoreContextResolver` (un solo lugar), no a nueve.

### 5.3 Admin

| Endpoint | Nuevo/Existente | Descripción |
|---|---|---|
| `POST /api/catalog/admin/merchants` | **Nuevo** | Alta de marca. |
| `POST /api/catalog/admin/merchants/{merchantId}/members` | **Nuevo** | Agrega un operador a la marca. |
| `PUT /api/catalog/admin/restaurants/{restaurantId}/merchant` | **Nuevo** | Mueve un local a una marca. |
| `POST /api/catalog/admin/restaurants` | Existente | Ahora acepta `merchantId` en lugar de (o además de) `ownerUserId`. |
| `PUT /api/catalog/admin/restaurants/{restaurantId}/owner` | Existente | Deprecado: se reinterpreta como "agregar el usuario como miembro del merchant". |

### 5.4 Internos — el punto que más duele

**El contrato actual es el cuello de botella real**: `GET
/api/internal/restaurants?userId=` devuelve **un** objeto
(`InternalCatalogController.java:96-100`) y tiene **dos** clientes
independientes que lo consumen como si fuera único:

| Consumidor | Método | Tipo devuelto | Uso |
|---|---|---|---|
| `orders-service` `CatalogHttpClientAdapter.java:94-118` | `findRestaurantIdByUserId` | `Optional<UUID>` | 5 use cases |
| `reviews-service` `HttpRestaurantLookupClientAdapter.java:37-47` | `findRestaurantIdByOwner` | `Optional<Long>` | 1 use case |

Estrategia **aditiva primero, ruptura después**:

| Fase | Endpoint | Estado |
|---|---|---|
| Actual | `GET /api/internal/restaurants?userId=` | Un objeto (404 si no hay). **Se mantiene** hasta la fase 3. |
| Nuevo | `GET /api/internal/owner/restaurants?userId=` | `List<InternalRestaurantResponse>`: todos los locales que el usuario puede operar. |
| Nuevo | `GET /api/internal/owner/restaurants/{restaurantId}/membership?userId=` | `204` si el usuario opera ese local, `404` si no. Es el endpoint que reemplaza las comparaciones de igualdad. |

`InternalRestaurantResponse` suma `merchantId` (campo aditivo, no rompe).

**Los consumidores que deben dejar de comparar igualdad:**

| Consumidor | Hoy | Debe pasar a |
|---|---|---|
| `orders-service` `UpdateOrderStatusUseCase.java:164` | `ownedRestaurantId.equals(order.getRestaurantId())` | `membership(userId, order.restaurantId)` |
| `orders-service` `GetOrderDetailUseCase.java:78` | igualdad con el único local | `membership(...)` |
| `orders-service` `ListOrdersUseCase.java:43` | filtra por un único `restaurantId` | filtro por local resuelto (header) o por todos los locales del merchant |
| `orders-service` `GetRestaurantSalesSummaryUseCase.java:55` | un único `restaurantId` | `restaurantId` opcional: con él, métricas del local; sin él, **agregado de todos los locales del merchant** (Q5 cerrado) |
| `orders-service` `GetAccountDeletionBlockersUseCase.java:38` | un único local | **todos** los locales del usuario (si no, se podrían cancelar pedidos de un local que se está borrando) |
| `reviews-service` `CreateReviewUseCaseImpl.java:181-185` | `findRestaurantIdByOwner(...) == order.restaurantId()` | `membership(...)` |

El punto 5 (borrado de cuenta) es el que más fácil se pasa por alto y el que
más caro sale si se olvida: hoy `EraseRestaurantOwnerUseCase.java:23`
(`restaurants.clearOwner(userId)`) asume un solo local.

### 5.5 Gateway

El gateway sanitiza únicamente los headers `x-jwt-claim-*`
(`gateway/src/middleware/jwt-auth/plugin.ts:233-242`), así que
`X-My-Store-Restaurant` debería pasar sin cambios. **A verificar**: si el
gateway tiene una allowlist de headers reenviados, hay que agregar el nuevo.
Si no la tiene, no se toca el gateway.

| `orders-service` | 6 use cases de autorización y scope, adapter HTTP, contrato interno | **Medio** |
| `reviews-service` | 1 use case + adapter | **Bajo** |
| `delivery-service` | Una migración nueva (`V11`) con `merchant_id` en `delivery_routes`, el campo en el dominio y en la entidad JPA. | **Bajo** |

| `apps/web` | Selector de local en el panel de tienda. | **Medio** |

### 6.1 Lo que NO se toca (y por qué)

- **`orders.restaurant_id`** — sigue siendo la identidad operativa del pedido.
  Un pedido es de un local, no de una marca.
- **`order_policies`** (`V9__order_policies.sql:17-37`, una política por
  `restaurant_id` con `uq_order_policies_restaurant`) — las políticas son por
  local: un local puede tener un radio y un SLA distintos. La fila global
  (`restaurant_id IS NULL`) sigue sirviendo de default.
- **`restaurant_hours`, `delivery_radius_km`, coordenadas, `products`** — son
  por local. Un local abre y cierra distinto. Los catálogos **no se comparten**
  entre locales de la misma marca (Q2 cerrado): cada local tiene su propia
  carta, con sus precios y su disponibilidad.
- **`reviews.target_id`** — sigue apuntando a `restaurant.id`. Una reseña es
  de un local concreto.
- **`delivery_routes`** — el snapshot de pickup (`ConfirmPaymentUseCase.java:140-157`)
  es por local: nombre, dirección y coordenadas del local. A partir de D10 suma
  también `merchant_id`, para que el repartidor pueda auditar a qué marca
  pertenece el local del pickup.

## 9. Riesgos y rollback

| Riesgo | Mitigación | Rollback |
|---|---|---|
| **IDOR en orders-service**: cambiar la comparación por igualdad a una consulta de pertenencia abre la puerta a que un operador toque pedidos de otro merchant | La pertenencia se valida contra `catalog-service`, no contra un claim del cliente. Test explícito: usuario con dos locales no puede tocar un pedido de un tercero | Revert del slice T5 |
| **Backfill incorrecto**: dos locales del mismo dueño en el backfill producen dos merchants distintos (o uno compartido por error) | El backfill es 1:1 por definición sobre el estado actual. Test de migración que verifica `count(merchants) == count(distinct user_id)` y `count(merchant_members) == count(distinct user_id)` | Revert de V13 (la tabla se puede dropear) |
| **Drop del `UNIQUE` en producción con datos que lo violan** | Antes de V14, un query de verificación: `select user_id from restaurant where user_id is not null group by user_id having count(*) > 1` debe devolver **cero filas**. Si devuelve filas, hay dos locales del mismo dueño y hay que fusionarlos en un merchant antes | V14 es reversible en la práctica (`alter table ... add constraint ... unique`) salvo que ya exista un duplicado |
| **Contrato interno roto en un consumidor no encontrado** | Búsqueda exhaustiva de `?userId=` en los tres consumidores (catalog, orders, reviews) + tests de contrato con `MockRestServiceServer` | El endpoint viejo sigue vivo hasta la fase 3 |
| **`merchant_id` desalineado entre orders y delivery** | El mismo nombre de campo en las tres capas (`InternalRestaurantResponse.merchantId` → `RestaurantInfo` → `delivery_routes.merchant_id`), verificado por test de contrato en orders **y** en delivery | Revert de T5 y T6 por separado |
| **El gateway descarta el header de contexto** | Verificar la allowlist de headers del gateway antes de la fase 2; si no está, el header viaja y no hay cambio | Header alternativo por query param sólo para el panel web |

## 10. Decisiones abiertas

| # | Pregunta | Opciones | Recomendación |
|---|---|---|---|
| Q1 | ¿El nombre que ve el cliente en el marketplace es el de la marca o el del local? | (a) marca + sucursal, (b) sólo el del local | **CERRADA: (a).** Se muestra `"<merchantName> — <restaurant.name>"`. `RestaurantResponse` suma `merchantName`; el `name` actual del restaurante pasa a ser el nombre de la sucursal. No hace falta migración de datos. |
| Q2 | ¿El catálogo se comparte entre locales? | (a) no, (b) sí con variantes por local | **CERRADA: (a).** Cada local tiene su propia carta, con sus precios y su disponibilidad. Compartir catálogo con variantes por local es un change aparte, con otro modelo de datos. |
| Q3 | ¿Quién puede crear locales? | (a) sólo `DUEÑO`, (b) también `ENCARGADO` | **CERRADA: (a).** `POST /api/catalog/my/restaurants` exige rol `DUEÑO` en `merchant_members`; un `ENCARGADO` recibe `403`. Crear un local es una decisión de la marca, no del local. |
| Q4 | ¿Se agrega `merchant_id` al snapshot de pickup en `delivery-service`? | (a) sí, para trazabilidad, (b) no, `restaurant_id` alcanza | **CERRADA: (a).** `delivery_routes` suma `merchant_id` (migración `V11` en delivery-service). Hoy el repartidor no puede auditar de qué local salió el pedido; con multi-local eso deja de ser un detalle. |
| Q5 | ¿El resumen de ventas se agrega entre locales? | (a) sólo por local, (b) por local y agregado de marca | **CERRADA: (b).** `GET /api/orders/store/summary` acepta `restaurantId` opcional: con él, métricas del local; sin él, agregado de todos los locales del merchant. |
| Q6 | ¿Los locales sin merchant quedan permitidos? | (a) sí, `merchant_id` nullable para siempre, (b) no, todo local tiene marca | **CERRADA: (a), con condición.** Un local sin marca sólo es admisible **si no tiene dueño** (el restaurante huérfano que crea el admin en `V6`). En cuanto se le asigna un dueño, o se le suman locales hermanos, la marca tiene que existir: al crear el segundo local, el merchant se crea automáticamente si el usuario todavía no tenía uno. Invariante: *todo restaurante con `user_id` no nulo tiene `merchant_id` no nulo*. |
