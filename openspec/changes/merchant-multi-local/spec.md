# Spec: `merchant-multi-local`

## 1. Overview

Este spec formaliza el soporte de **multi-local** en FlashDrop: una entidad
`merchant` (la marca) que posee N `restaurant` (los locales), con una relación
N:M de operadores (`merchant_members`).

El sistema actual modela "tienda = dueño" en 1:1 estricto, y esa restricción
está en cuatro capas: el `UNIQUE(user_id)` de `public.restaurant`
(`V1__create_schema.sql:11`, conservado por `V6__restaurant_owner_nullable.sql`),
los guards `OwnerAlreadyAssignedException` de `CreateRestaurantUseCase.java:37-39`
y `AssignRestaurantOwnerUseCase.java:27-31`, las queries que devuelven
`Optional<RestaurantEntity>` por `userId`, y el contrato interno
`GET /api/internal/restaurants?userId=` que devuelve **un** objeto.

El cambio es **aditivo por fases**. Las fases 1 y 2 (migraciones + backfill +
dual-write) no cambian el comportamiento observable de ninguna pantalla. La
fase 3 elimina el `UNIQUE(user_id)` — el único punto irreversible — y la fase 4
deprecia `restaurant.user_id`.

**Compatibilidad de datos**: `restaurant.id` no cambia. Los pedidos, las
reseñas y las rutas de reparto siguen apuntando al local. No hay migración de
ids.

**Público**: el marketplace y el flujo de pedido del cliente **no cambian**.
`POST /api/orders` sigue sin mandar `restaurantId`: se deriva de los productos
(`CreateOrderUseCase.java:88-103`). Con diez locales el marketplace muestra
diez filas y el cliente pide contra la que eligió.

## 2. Functional Requirements

### FR-1 — Entidad `merchant` y `merchant_members`

`catalog-service` es el dueño de las dos tablas nuevas, en `flashdrop_catalog`.

```sql
create table public.merchants (
    id          bigint generated by default as identity primary key,
    name        varchar(255) not null,
    legal_name  varchar(255),
    tax_id      varchar(64),
    phone       varchar(32),
    email       varchar(255),
    status      varchar(16) not null default 'ACTIVO',
    created_at  timestamp(6) not null default current_timestamp,
    updated_at  timestamp(6) not null default current_timestamp
);
create index idx_merchants_name on public.merchants(name);

create table public.merchant_members (
    id          bigint generated by default as identity primary key,
    merchant_id bigint not null references public.merchants(id) on delete cascade,
    user_id     bigint not null,
    role        varchar(16) not null default 'DUEÑO',
    created_at  timestamp(6) not null default current_timestamp,
    constraint uq_merchant_member unique (merchant_id, user_id)
);
create index idx_merchant_members_user on public.merchant_members(user_id);
```

- `merchants.name` **no** es `unique`: dos marcas con el mismo nombre comercial
  son legales.
- `merchant_members.user_id` **no** tiene FK a `auth.users`: `catalog-service`
  no es dueño de la base de auth (AGENTS.md §2). Es una referencia lógica, igual
  que `restaurant.user_id` hoy.
- `role` ∈ {`DUEÑO`, `ENCARGADO`}.
- `restaurant.merchant_id` es `bigint` **nullable**, con FK a `merchants(id)`
  `on delete restrict`: borrar una marca no borra locales con historial de
  pedidos.

**Invariante (D11)**: todo restaurante con `user_id` no nulo tiene
`merchant_id` no nulo. Un local sin marca sólo es admisible si **no tiene
dueño** (el restaurante huérfano que crea el admin, habilitado por
`V6__restaurant_owner_nullable.sql`).

### FR-2 — Migraciones y backfill

Migraciones Flyway en `services/catalog-service/src/main/resources/db/migration/`:

| Migración | Contenido | Reversible |
|---|---|---|
| `V11__create_merchants.sql` | `merchants` + `merchant_members` | Sí |
| `V12__add_restaurant_merchant_id.sql` | `restaurant.merchant_id` nullable + índice | Sí |
| `V13__backfill_merchant.sql` | Backfill 1:1 | Sí |
| `V14__drop_restaurant_user_id_unique.sql` | Drop del `UNIQUE(user_id)` + remoción de los guards `OwnerAlreadyAssigned` | **No** (fase 3) |

El backfill es **1:1 con el estado actual**: un usuario con un restaurante
produce un merchant con un local y un `merchant_member` con rol `DUEÑO`. No hay
pérdida de información y ningún endpoint cambia de comportamiento.

**Queries de control obligatorios antes de `V14`** (ambos deben devolver cero
filas):

```sql
-- dos locales del mismo dueño (requiere fusión previa)
select user_id from public.restaurant
where user_id is not null
group by user_id having count(*) > 1;

-- invariante D11
select count(*) from public.restaurant
where user_id is not null and merchant_id is null;
```

### FR-3 — Contexto de local activo

Los endpoints de dueño operan sobre **un** local, elegido por el header
`X-My-Store-Restaurant` (id del local, Long).

Regla de resolución, en este orden:

1. **Header presente** → el local debe pertenecer a un merchant del usuario.
   Si no → `403`.
2. **Header ausente** y el usuario tiene exactamente **un** local → ese local.
   (Compatibilidad total con el comportamiento actual.)
3. **Header ausente** y el usuario tiene **varios** locales → `400` con código
   `LOCAL_CONTEXT_REQUIRED` y la lista de locales disponibles en el body.

| Código | Cuándo |
|---|---|
| 200 | Local resuelto. |
| 400 | Sin header y más de un local (`LOCAL_CONTEXT_REQUIRED`). |
| 401 | Sin JWT o JWT inválido. |
| 403 | El local del header no pertenece al usuario. |
| 404 | El local del header no existe. |

El contexto **no** viaja en el JWT: el token es de largo plazo y no debe
transportar estado de sesión del panel.

### FR-4 — Endpoints de dueño nuevos

| Endpoint | Descripción |
|---|---|
| `GET /api/catalog/my/restaurants` | Locales operables por el usuario. `List<RestaurantResponse>`. |
| `GET /api/catalog/my/merchant` | Ficha de la marca: `name`, `legalName`, `phone`, `email`, `status`. |
| `POST /api/catalog/my/restaurants` | Crea un local dentro del merchant. |

`POST /api/catalog/my/restaurants`:

```json
{ "name": "Sucursal Centro", "address": "Av. Siempre Viva 742",
  "latitude": -34.6037, "longitude": -58.3816, "deliveryRadiusKm": 4.0 }
```

- El local creado queda con `merchant_id` del merchant del usuario.
- Si el usuario **no tenía** merchant, se crea uno automáticamente con `name`
  = nombre de la marca inicial (D11).
- Sólo un `DUEÑO` puede crear locales: un `ENCARGADO` recibe `403` (D9).
- El local nace **cerrado** (`accepting_orders = false`), igual que el alta
  administrativa actual (`CreateRestaurantUseCase`): el dueño lo abre cuando
  configura su horario.

| Código | Cuándo |
|---|---|
| 201 | Local creado. |
| 400 | Body inválido, `name` en blanco, coordenadas inconsistentes. |
| 401 | Sin JWT o JWT inválido. |
| 403 | El usuario no es `DUEÑO` de ningún merchant. |

### FR-5 — Endpoints de dueño existentes

Operan sobre el local resuelto por FR-3. No cambia su ruta, su método ni la
forma de la respuesta.

| Endpoint | Efecto |
|---|---|
| `GET /api/catalog/my/restaurant` | Devuelve el local resuelto. |
| `PUT /api/catalog/my/restaurant/open-status` | `acceptingOrders` del local resuelto. |
| `PUT /api/catalog/my/restaurant/hours` | Horarios del local resuelto. |
| `PUT /api/catalog/my/restaurant/location` | Coordenadas del local resuelto. |
| `PUT /api/catalog/my/restaurant/delivery-radius` | Radio de reparto del local resuelto. |
| `GET /api/catalog/my/products` | Productos **del local resuelto**. |
| `POST /api/catalog/my/products` | El producto se crea en el local resuelto. |
| `PUT /api/catalog/my/products/{productId}` | 403 si el producto pertenece a otro local del usuario. |
| `DELETE /api/catalog/my/products/{productId}` | 403 si el producto pertenece a otro local del usuario. |

Regla de autorización: un producto sólo es operable si su `restaurant_id` es el
local resuelto. Un `ENCARGADO` no puede tocar los locales de otro merchant.

### FR-6 — Endpoints admin

| Endpoint | Descripción |
|---|---|
| `POST /api/catalog/admin/merchants` | Alta de marca. |
| `POST /api/catalog/admin/merchants/{merchantId}/members` | Agrega un operador (`userId`, `role`). |
| `PUT /api/catalog/admin/restaurants/{restaurantId}/merchant` | Mueve un local a una marca. |
| `POST /api/catalog/admin/restaurants` | Ahora acepta `merchantId` además de `ownerUserId`. |
| `PUT /api/catalog/admin/restaurants/{restaurantId}/owner` | Deprecado: se reinterpreta como "agregar el usuario como miembro del merchant". |

Asignar un dueño a un restaurante que ya tiene dueño **no** lanza
`OwnerAlreadyAssignedException` anymore: el usuario se agrega como miembro del
merchant.

### FR-7 — Contrato interno de ownership

Endpoints nuevos en `catalog-service`, protegidos por `X-Internal-Api-Key`:

```
GET /api/internal/owner/restaurants?userId={userId}
GET /api/internal/owner/restaurants/{restaurantId}/membership?userId={userId}
```

- El primero devuelve `List<InternalRestaurantResponse>`: todos los locales
  que el usuario puede operar. Vacío si no tiene ninguno.
- El segundo devuelve `204` si el usuario opera ese local, `404` si no.
- `InternalRestaurantResponse` suma el campo aditivo `merchantId`. El JSON
  anterior sigue deserializando en los consumidores existentes.

El endpoint actual `GET /api/internal/restaurants?userId=` **se mantiene** con
su forma actual (un objeto, 404 si no hay) hasta la fase 3.

### FR-8 — Autorización por pertenencia en `orders-service`

Los cinco use cases que hoy comparan igualdad con un único local consultan
pertenencia:

| Use case | Comportamiento |
|---|---|
| `UpdateOrderStatusUseCase.java:164` | El operador puede cambiar el estado de un pedido **de cualquiera de sus locales**; de un tercero → `403`. |
| `GetOrderDetailUseCase.java:78` | Ídem: el detalle de un pedido de un tercero → `403`. |
| `ListOrdersUseCase.java:43` | Devuelve los pedidos del local resuelto o de todos los locales del merchant. |
| `GetRestaurantSalesSummaryUseCase.java:55` | FR-10. |
| `GetAccountDeletionBlockersUseCase.java:38` | Detecta pedidos activos en **todos** los locales del usuario. |

Regla dura: la pertenencia se valida **contra `catalog-service`**, nunca contra
un claim del cliente. Un token de un merchant no habilita locales ajenos.

### FR-9 — Autorización por pertenencia en `reviews-service`

`CreateReviewUseCaseImpl.java:181-185` deja de comparar igualdad con el único
local del autor y pasa a consultar la pertenencia: el dueño de dos locales
puede calificar un pedido de cualquiera de los dos; un usuario que no opera el
local del pedido recibe `403`.

### FR-10 — Resumen de ventas por local y agregado

`GET /api/orders/store/summary` acepta `restaurantId` **opcional**:

- Con `restaurantId` → métricas de ese local.
- Sin `restaurantId` → **agregado de todos los locales del merchant** del
  usuario.

Ningún usuario puede obtener el resumen de un local que no opera → `403`.

### FR-11 — Trazabilidad de la marca en el reparto (D10)

`delivery_routes` suma la columna `merchant_id` (nullable, migración `V11` de
`delivery-service`).

- `orders-service` lo obtiene de `InternalRestaurantResponse.merchantId` y lo
  incluye en el snapshot de pickup que envía a `delivery-service` al confirmar
  el pago (`ConfirmPaymentUseCase.java:140-157`).
- Una ruta creada antes de la migración tiene `merchant_id` null y su lectura
  no falla.
- El repartidor puede auditar a qué marca pertenece el local del pickup.

### FR-12 — Nombre visible "Marca — Sucursal" (D6)

`RestaurantResponse` suma el campo aditivo `merchantName`. El nombre visible se
arma como `"<merchantName> — <restaurant.name>"`, donde `restaurant.name` pasa
a ser el **nombre de la sucursal**.

- No requiere migración de datos: el nombre actual del restaurante pasa a ser el
  de la sucursal.
- El JSON anterior sigue deserializando en los clientes existentes.

### FR-13 — Gateway

El header `X-My-Store-Restaurant` debe llegar intacto a `catalog-service`. El
gateway sanitiza únicamente los headers `x-jwt-claim-*`
(`gateway/src/middleware/jwt-auth/plugin.ts:233-242`); si existe una allowlist
de headers reenviados, debe incluir el nuevo.

### FR-14 — Web: selector de local

- El panel de tienda lista los locales del merchant (`GET /api/catalog/my/restaurants`).
- Cada local se muestra como "Marca — Sucursal".
- El local seleccionado viaja en `X-My-Store-Restaurant` en cada llamada de
  dueño.
- Si la respuesta es `400 LOCAL_CONTEXT_REQUIRED`, la UI ofrece elegir local en
  lugar de mostrar un error vacío.

### FR-15 — Borrado de cuenta y de dueño

`EraseRestaurantOwnerUseCase.java:23` deja de resolver un único local:

- Al borrarse la cuenta de un usuario, se eliminan sus filas de
  `merchant_members`.
- Si el merchant se queda sin miembros, **se conserva** junto con sus locales
  y su catálogo — el mismo criterio que `V6` aplica hoy a los restaurantes sin
  dueño.
- `GetAccountDeletionBlockersUseCase.java:38` bloquea el borrado si hay pedidos
  activos en **cualquier** local del usuario.

### FR-16 — Rol `ENCARGADO`

Un `ENCARGADO` es miembro del merchant y opera sus locales con los mismos
permisos que el `DUEÑO`, **excepto** la creación de locales (FR-4) y la
gestión de la ficha de la marca.

## 3. Non-goals

- Catálogo compartido entre locales, con precio o disponibilidad por local.
  Cada local tiene su propia carta (D7).
- Facturación consolidada por marca y reparto de ingresos entre locales.
- Roles finos por local más allá de `DUEÑO` / `ENCARGADO`.
- Analítica multi-local y panel de marca.
- Migración de las implementaciones legacy de `juniors/`.
- Cambios en `auth-service`: los roles siguen siendo de plataforma.
- Cambios en el flujo de pedido del cliente (`POST /api/orders` no cambia).
- Migración de ids de `restaurant`.
